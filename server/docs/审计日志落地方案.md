# 审计日志落地方案

## 1. 文档定位

本文总结当前项目审计实现中值得复用的设计思想，用于指导在一个新的工程中从零建设一套独立的审计日志能力。

新工程不依赖、不复制发布当前项目的 `smile-audit-starter` 制品，也不要求沿用当前项目的包名、Maven 坐标、Sa-Token、数据库表或异常体系。实施时应结合新工程真实的认证、异常、事务、线程池、数据库和权限模型重新设计代码。

本文参考当前项目中的以下实践，但只提炼方法：

- 注解声明与 AOP 拦截；
- 编程式审计入口；
- 操作人、目标和动作的事件快照；
- 事务提交后发布成功事件；
- 异步、独立事务、幂等落库；
- 本地事件向 Outbox/MQ 的可演进边界；
- 审计查询的数据权限与敏感信息控制。

## 2. 建设目标与非目标

### 2.1 建设目标

新工程建设完成后，应具备以下能力：

1. 业务开发者可以通过注解声明大部分审计行为；
2. 登录、认证失败、定时任务等特殊流程可以通过编程式 API 记录；
3. 审计数据保存事件发生时的操作人、动作、目标、结果和链路快照；
4. 成功审计只在业务事务提交后产生，业务回滚不产生伪成功记录；
5. 审计构造、发布或落库失败不覆盖原业务返回和异常；
6. 异步消费者按全局事件 ID 幂等写入；
7. 密码、验证码、Token、密钥和完整敏感标识不会进入审计事件；
8. 审计查询执行真实的接口权限、租户权限、组织权限和数据权限；
9. 可以从进程内异步落库逐步升级到 Outbox/MQ 可靠投递，而不重写业务注解；
10. 具备监控、告警、容量、保留、归档和故障恢复机制。

### 2.2 非目标

- 审计日志不能代替业务日志、链路追踪或监控指标；
- 审计切面不能承担业务校验、权限校验或数据转换；
- 不自动序列化全部请求、响应或 Entity；
- 不通过同步远程调用让审计平台参与业务事务；
- 不为了“全覆盖”给所有查询方法和内部方法批量添加审计；
- 第一阶段不必直接建设中心化大数据审计平台。

## 3. 开工前必须确认的事项

新工程不能直接照搬当前项目字段。编码前应先完成以下决策：

| 决策项 | 必须确认的内容 |
| --- | --- |
| 技术基线 | Java、Spring Boot、AOP、事务框架、数据库、ORM/Mapper、消息中间件 |
| 认证模型 | 登录 ID 格式、用户类型、租户、机构、应用端、会话字段及可信来源 |
| 异常模型 | 业务错误码如何提取，哪些错误属于拒绝，哪些属于系统失败 |
| 网关链路 | 客户端 IP 如何清洗和传递，TraceId 使用哪个 MDC Key |
| 数据所有权 | 每个服务独立存储，还是统一审计服务存储 |
| 可靠性等级 | 是否允许进程异常窗口内丢失，是否必须 Outbox/MQ |
| 数据治理 | 敏感字段、完整 IP 政策、在线保留、归档、清理和备份期限 |
| 查询权限 | 平台、租户、机构、个人分别能查看哪些数据 |
| 容量指标 | 日事件量、峰值 TPS、查询时间跨度、可接受落库延迟 |

无法从新工程代码和已确认需求中得到的信息必须标记 `TODO(待确认)`，不得猜测会话字段、权限码、表字段、请求头或保留期限。

## 4. 总体架构

### 4.1 推荐模块划分

建议在新工程中按职责拆成四层。可以是独立 Maven 模块，也可以先在单工程内用清晰包边界实现。

```text
audit-contract
  ├─ 审计注解
  ├─ 审计命令、操作人快照、审计事件
  ├─ 结果与主体类型枚举
  └─ 身份、IP、TraceId、失败分类、事件发布 SPI

audit-core
  ├─ AOP 切面
  ├─ SpEL/表达式解析
  ├─ 事件构造器
  ├─ 事务提交后发布
  └─ 编程式记录入口

audit-infrastructure
  ├─ 本地事件或 Outbox/MQ 发布器
  ├─ 异步监听器
  ├─ Entity、Mapper、Writer
  ├─ 数据库表与索引
  └─ 监控指标

audit-application
  ├─ 审计查询 Service
  ├─ 数据权限
  ├─ Controller、DTO、VO
  ├─ 导出与审批
  └─ 数据保留与归档任务
```

核心原则是：业务声明、事件契约、发布方式和存储方式相互解耦。业务代码只依赖注解或记录接口，不感知最终使用本地事件、Outbox 还是 MQ。

### 4.2 标准执行链路

```text
请求进入
  -> 网关清洗客户端 IP 并生成/透传 TraceId
  -> 认证与权限校验
  -> 公共业务 Service 方法
  -> 审计切面在原线程捕获操作人和请求链路快照
  -> 执行业务方法
  -> 构造审计事件
  -> 成功：业务事务提交后发布
  -> 失败/拒绝：按策略发布失败事件
  -> 有界线程池异步消费
  -> 独立新事务幂等落库
  -> 受权限保护的分页查询
```

登录前流程、认证失败和系统任务不强行套用当前登录人解析器，而是由业务在可信信息产生后显式调用编程式记录入口。

## 5. 核心模型设计

### 5.1 操作人快照

建议定义不可变 `AuditActor`，至少包含：

| 字段 | 含义 |
| --- | --- |
| `tenantId` | 可选租户 ID |
| `operatorType` | 用户、平台管理员、系统、匿名等稳定类型 |
| `operatorId` | 操作人 ID，系统或匿名使用明确约定值 |
| `organizationId` | 事件发生时所在机构 ID |
| `username` | 用户名快照 |
| `displayName` | 显示名称快照 |
| `appCode` | 事件发生时所处应用端编码 |

操作人必须在原业务线程、身份上下文仍然有效时形成快照。异步线程不得再次读取登录上下文，也不得在查询时反查当前用户名替代历史快照。

### 5.2 审计命令

建议定义 `AuditRecordCommand` 表达“想记录什么”，但不包含运行结果和运行时自动字段。至少包括：

- 来源 `source`；
- 中文分类路径 `categoryPath`；
- 动作编码和动作名称；
- 目标类型、ID、名称、业务编码；
- 操作原因；
- 必要的脱敏业务字段；
- 可选客户端 IP 和设备摘要；
- 后端确认的操作人快照。

### 5.3 审计事件

建议定义不可变、可版本化的 `AuditEvent`，包含：

- 全局唯一 `eventId`；
- `schemaVersion`；
- 审计命令中的全部快照字段；
- `SUCCESS`、`FAILURE`、`DENIED` 等结果；
- 稳定失败原因码；
- TraceId、发生时间和执行耗时；
- 客户端 IP 或摘要；
- 操作人快照。

事件契约一旦进入 MQ 或被多个服务消费，应遵循以下演进规则：

- 新增可选字段优先，禁止随意删除和改义；
- 枚举新增值时消费者必须具备未知值兼容能力；
- 不兼容变更提升 `schemaVersion`；
- 消费者至少兼容当前版本和上一稳定版本；
- 对事件建立契约测试和固定样例。

### 5.4 动作编码

建议统一为：

```text
<domain>:<resource>:<action>
```

例如：

```text
account:user:create
account:role:grant
auth:login:password
order:purchase:approve
```

规则：

- `actionCode` 发布后永久保留，不修改含义、不复用；
- `actionName` 是事件发生时的中文快照；
- `source` 使用稳定服务或业务域编码；
- `targetType` 使用业务类型，不使用 Java 类名；
- `categoryPath` 用于审计展示，不与菜单、路由或权限资源强绑定；
- 建立集中动作目录，在评审阶段检查重复编码和含义冲突。

## 6. 核心组件设计

### 6.1 审计注解

新工程可以定义类似以下语义的注解，名称可按工程规范确定：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface AuditOperation {
    String source();
    String[] categoryPath() default {};
    String actionCode();
    String actionName();
    String targetType();
    String targetId();
    String targetName() default "";
    String targetCode() default "";
    String reason() default "";
    boolean recordFailure() default true;
}
```

注解只描述审计元数据，不执行权限判断，也不自动收集整个请求对象。

使用约束：

- 只放在由 Spring AOP 代理调用的公共 Service 方法；
- 私有方法、静态方法和类内自调用不能依赖代理切面；
- 新工程编译必须保留方法参数名，例如 Maven 开启 `<parameters>true</parameters>`；
- 表达式应保持简单，只引用明确的方法参数、返回值、异常和操作人；
- DTO 字段或方法参数重命名时必须同步调整表达式并运行测试；
- 目标 ID 必须能唯一定位目标，不应静默回退为操作人 ID。

### 6.2 表达式求值器

表达式上下文建议只暴露：

```text
#方法参数名
#result
#error
#actor
```

安全要求：

- 只求值注解显式声明的字段；
- 不自动序列化参数、返回值或异常对象；
- 表达式失败记录方法和字段信息，不打印敏感值；
- 表达式失败是否跳过事件或将字段置空，需要按字段重要性设计；
- `source`、`actionCode`、`actionName`、`targetType` 等必填字段缺失时不生成残缺事件；
- 复杂业务判断应在 Service 中形成明确、已脱敏的上下文，不写入复杂 SpEL。

### 6.3 操作人解析器

定义 `AuditActorResolver` 接口，由新工程的认证适配层实现。

实现原则：

- 从真实登录上下文、Token Session 或服务端鉴权结果读取；
- 不从 Controller DTO、自报请求头或前端隐藏字段读取身份；
- 明确支持用户、平台身份、系统和匿名主体；
- 会话字段缺失时不能伪造，应降级并产生监控指标；
- 如果补齐名称需要查询数据库，应评估请求延迟，优先在建立会话时固化名称；
- 同一个应用上下文只能有一个明确生效的解析器。

### 6.4 客户端 IP 与 TraceId 解析器

定义独立的 `ClientIpResolver` 和 `TraceIdResolver`，不要在切面里硬编码网关请求头和 MDC Key。

客户端 IP 规则：

1. 网关先移除外部请求携带的内部可信 IP 头；
2. 网关依据受信任代理链计算真实客户端 IP；
3. 网关写入内部可信头；
4. 下游只读取该头或受控回退到远端地址；
5. 异步切换前完成快照；
6. 是否保存完整 IP 由数据治理策略决定，也可以只保存不可逆摘要。

TraceId 应在请求入口生成，并统一写入 MDC。系统任务和消息消费也应建立自己的 TraceId 或关联 ID。

### 6.5 失败分类器

不要让审计核心依赖新工程的具体业务异常类。建议定义 `AuditFailureClassifier`：

```text
Throwable -> result + failureReasonCode
```

默认规则可以是：

- 认证失败、权限不足、业务规则明确拒绝：`DENIED`；
- 其他业务异常和系统异常：`FAILURE`；
- 原业务异常必须原样继续抛出；
- 审计只保存稳定错误码，不保存可能包含敏感信息的异常消息和堆栈正文。

### 6.6 事件记录器

事件记录器统一服务于注解入口和编程式入口，负责：

- 校验必填字段；
- 生成 `eventId` 和 `schemaVersion`；
- 合并操作人、IP、TraceId 等快照；
- 计算执行耗时；
- 将异常分类为结果和失败码；
- 安全调用事件发布器；
- 捕获审计自身异常，保持原业务行为不变。

### 6.7 AOP 切面

切面顺序必须与事务切面协同，核心流程为：

```text
捕获操作人/IP/TraceId和开始时间
  -> 调用原业务方法
  -> 成功：构造成功命令并注册事务提交后发布
  -> 异常：按配置构造失败事件
  -> 原返回值或原异常保持不变
```

必须通过测试验证实际代理顺序，不能只根据注解顺序推断事务已经提交。

### 6.8 编程式入口

以下场景使用编程式入口：

- 登录成功和登录失败；
- 密码找回、验证码校验、恢复码等登录前流程；
- 消息消费、定时任务和批处理；
- 操作人只能在业务中途经服务端校验后确定的流程；
- 一个方法需要产生多个语义不同的审计事件。

编程式入口的操作人必须来自后端已经验证完成的上下文。身份未确认的失败登录使用匿名主体，不能用原始用户名或账号 ID 冒充真实操作人。

## 7. 事务、异步与一致性

### 7.1 成功事件

有本地业务事务时，成功事件应在事务成功提交后发布；事务回滚时不产生成功审计。无事务时，在方法成功返回后发布。

不要在主业务事务中直接写远程审计服务，也不要等待 MQ 或第三方平台响应，否则会扩大事务、增加耦合并把审计故障传播给业务。

### 7.2 失败和拒绝事件

失败事件是否立即发布取决于业务事务状态和审计要求。至少需要保证：

- 不因失败审计覆盖原异常；
- 不读取已经失效的异步登录上下文；
- 失败事件不保存异常中的敏感正文；
- 对高频失败场景进行容量和恶意流量评估。

### 7.3 异步执行器

使用有界、命名、可观测的线程池，明确：

- 核心线程数与最大线程数；
- 有界队列容量；
- 线程名前缀；
- 拒绝策略；
- 停机等待时间；
- 未捕获异常处理；
- 活跃线程、队列深度、拒绝次数等指标。

禁止使用 `new Thread()`、临时创建线程池或默认公共 `CompletableFuture` 线程池。审计量较大时应使用独立审计线程池，避免与文件、消息或第三方调用互相挤占。

### 7.4 独立事务 Writer

异步 Writer 使用独立新事务，完成：

1. `AuditEvent -> Entity` 显式转换；
2. 字段长度限制；
3. 敏感字段白名单和脱敏；
4. 分类路径等结构化字段序列化；
5. 按 `eventId` 幂等插入；
6. 写入失败只记录事件 ID、动作编码和异常类型，不打印事件敏感正文。

## 8. 数据库设计

### 8.1 推荐字段

| 字段组 | 推荐字段 |
| --- | --- |
| 事件标识 | `id`、`event_id`、`schema_version`、`source_code` |
| 分类与动作 | `category_path_snapshot`、`action_code`、`action_name_snapshot` |
| 操作人快照 | `tenant_id`、`operator_type`、`operator_id`、`operator_organization_id`、`operator_username_snapshot`、`operator_display_name_snapshot`、`app_code_snapshot` |
| 目标快照 | `target_type`、`target_id`、`target_name_snapshot`、`target_code_snapshot` |
| 结果信息 | `reason`、`result`、`failure_reason_code`、`duration_ms` |
| 链路信息 | `ip_address` 或摘要、`ip_hash`、`device_summary`、`trace_id`、`occurred_time` |
| 管理字段 | `created_time` 等新工程统一字段 |

字段仅为设计参考。最终类型、长度、必填性、主键策略和管理字段必须依据新工程规范确定。

### 8.2 表设计原则

- 审计表只追加，普通业务接口不得修改或删除历史记录；
- `event_id` 建唯一约束；
- 冲突处理应明确限定 `event_id`，不要用无条件忽略全部约束错误；
- 为租户、机构、动作、结果、操作人、发生时间等常用条件设计索引；
- 大数据量提前考虑按时间分区、冷热分层和归档；
- 列表强制分页并限制页大小；
- 不使用 `SELECT *`；
- 数据权限条件下推 SQL，禁止查全量后在 Java 中过滤；
- 表和字段注释遵循新工程数据库规范；
- PostgreSQL 专属行为必须在真实 PostgreSQL 或 Testcontainers 中验证。

### 8.3 幂等落库

推荐使用：

```text
全局唯一 eventId
  + 数据库唯一约束
  + 明确的 eventId 冲突忽略/返回成功
```

验收时必须并发投递同一事件，确认只产生一条记录。其他字段违反非空、长度或外键等约束时应暴露真实错误，不能被误判为重复事件。

## 9. 查询、权限与数据治理

### 9.1 查询能力

第一阶段建议只提供必要查询条件：

- 时间范围；
- 动作编码；
- 结果；
- 操作人；
- 目标类型与目标 ID；
- 租户和机构范围；
- TraceId 或事件 ID 精确查询。

查询必须分页、限制最大时间跨度，并按 `occurred_time DESC, id DESC` 等稳定顺序排序。大数据量场景使用游标或时间与主键联合翻页。

### 9.2 权限控制

- 平台管理员只能按已授权范围查看平台或租户审计；
- 租户管理员只能查看本租户；
- 机构管理员按组织数据权限下推 SQL；
- 普通用户如允许查看，只能查看与自身有关的数据；
- 审计导出属于敏感操作，应单独授权、限制范围，并对导出动作本身进行审计；
- 不依赖前端隐藏按钮完成权限控制。

具体权限码必须由新工程权限模型确认，本文不预设。

### 9.3 敏感信息

禁止进入事件、日志、数据库和死信载荷的内容包括：

- 密码和密码哈希；
- 验证码、Token、Session、Cookie；
- 私钥、AccessKey、Secret；
- 完整手机号、证件号、银行卡号；
- 未经白名单确认的请求/响应 JSON；
- 包含敏感正文的异常消息。

手机号等标识仅保存脱敏快照或不可逆摘要。完整 IP 是否保存必须经过安全和合规确认。

- 分区创建、归档和清理是否需要调度平台。

## 10. 两级可靠性方案

### 10.1 一级：进程内事件 + 异步落库

```text
业务方法
  -> 事务提交后发布进程内事件
  -> 有界线程池
  -> 独立事务幂等写审计表
```

优点是实现简单、改造成本低。缺点是业务提交后、异步写库前如果进程退出，事件可能丢失；监听失败通常只能依赖日志和告警人工处理。

适用于允许少量丢失窗口的普通运营审计或首期试点。

### 10.2 二级：本地 Outbox + MQ

```text
业务事务
  -> 同事务写本地 Outbox
  -> 可靠投递任务
  -> MQ
  -> 幂等消费者
  -> 审计存储
```

Outbox 至少包含：事件 ID、事件类型、schema 版本、载荷、载荷摘要、状态、重试次数、下次投递时间、创建时间和最后错误摘要。

必须建设：

- 有限重试和指数退避；
- 多实例安全领取；
- 死信和受控重放；
- 积压与延迟告警；
- 生产者与消费者对账；
- 消费端版本兼容和幂等；
- 载荷加密、访问控制或敏感字段最小化。

认证安全、权限变更、账号恢复等关键审计如果不能接受丢失，应直接选择二级方案。

## 11. 分阶段建设计划

### 阶段 0：需求与架构设计（建议 2～3 人日）

任务：

1. 盘点必须审计的业务动作；
2. 确认身份、异常、IP、TraceId、数据库和线程池模型；
3. 划分普通、敏感和合规关键事件；
4. 决定一级或二级可靠性；
5. 形成事件模型、动作编码、数据表、权限和保留策略设计；
6. 选取 3～5 个典型动作作为试点。

交付物：

- 审计事件字段字典；
- 动作编码目录初版；
- 架构设计与时序说明；
- 数据库设计；
- 敏感字段白名单/黑名单；
- 试点范围与验收用例。

### 阶段 1：建设审计契约与核心模块（建议 3～5 人日）

任务：

1. 新建审计注解、命令、操作人和事件模型；
2. 新建身份、IP、TraceId、失败分类和发布 SPI；
3. 实现表达式求值器；
4. 实现事件记录器和编程式入口；
5. 实现 AOP 切面及事务提交后回调；
6. 建立自动装配或应用装配；
7. 完成核心单元测试。

验收标准：

- 成功、失败、拒绝事件字段正确；
- 表达式只读取显式字段；
- 原业务异常和返回不受审计故障影响；
- 事务回滚不产生成功审计；
- 自定义 SPI 可以替换默认实现。

### 阶段 2：建设基础设施与存储（建议 3～5 人日）

任务：

1. 实现真实操作人、客户端 IP、TraceId 和异常分类适配器；
2. 建设有界审计线程池；
3. 创建审计表、索引、Entity、Mapper 和 Writer；
4. 实现 `eventId` 幂等落库；
5. 增加发布、线程池、落库和延迟指标；
6. 如果采用二级方案，同步建设 Outbox、投递器和消费者；
7. 完成数据库集成测试。

### 阶段 3：试点业务接入（建议 2～4 人日）

首批至少覆盖：

- 一个新增操作；
- 一个修改操作；
- 一个删除、停用或撤销操作；
- 一个业务拒绝；
- 一个登录前、系统任务或编程式审计流程。

接入过程中同步维护动作目录，逐项评审目标 ID、中文快照、操作原因和敏感字段。

### 阶段 4：查询与权限（建议 2～4 人日）

任务：

1. 建设分页查询 DTO、Service、Mapper、VO 和 Controller；
2. 落实平台、租户、机构和个人数据范围；
3. 限制页大小和查询时间跨度；
4. 验证索引与查询计划；
5. 如需导出，增加审批、数量限制和导出行为审计。

### 阶段 5：灰度、故障演练与推广（建议 2～4 人日）

任务：

1. 先执行数据库变更，再发布应用；
2. 灰度开启少量动作；
3. 观察业务延迟、队列深度、落库失败和数据库容量；
4. 演练数据库不可用、线程池拒绝、重复投递和应用退出；
5. 修正后冻结事件 schema 和首版动作目录；
6. 按高风险写操作优先的顺序扩大覆盖。

## 12. 测试与验收

### 12.1 核心单元测试

- 能从真实方法参数和返回值解析目标快照；
- 能在业务调用前捕获操作人；
- 成功事件包含正确动作、目标、时间和耗时；
- 401/403 或新工程定义的拒绝异常被正确分类；
- 原业务异常实例和错误码保持不变；
- 审计发布异常不改变成功返回；
- 必填表达式失败不会生成误导性审计；
- 登录前流程使用后端可信上下文；
- 敏感字段不进入事件。

### 12.2 事务与集成测试

- 事务提交后才出现成功事件；
- 事务回滚不出现成功事件；
- Writer 使用独立事务；
- 同一 `eventId` 并发写入只保留一条；
- 非 `eventId` 数据约束错误不会被静默忽略；
- 数据库不可用时业务行为符合既定隔离策略；
- PostgreSQL 行为使用真实 PostgreSQL/Testcontainers 验证。

### 12.3 安全测试

- 外部伪造可信 IP 头无效；
- 用户不能通过请求字段冒充操作人；
- 不记录密码、验证码、Token、密钥和完整手机号；
- 查询接口无法跨租户或越过组织范围；
- 导出受到独立权限和数量限制；
- 应用日志和死信不包含敏感事件正文。

### 12.4 性能与容量测试

- 评估切面与表达式对业务 P95/P99 的影响；
- 压测峰值事件下线程池队列和拒绝策略；
- 验证批量业务是否产生不可控事件风暴；
- 验证常用分页查询命中索引；
- 估算日增量、年度容量、索引大小和归档窗口。

## 13. 可观测性与告警

建议至少采集：

| 指标 | 建议处理 |
| --- | --- |
| 事件构造失败数 | 持续增长告警 |
| 事件发布失败数 | 生产出现即告警 |
| 用户请求降级为 SYSTEM 数 | 异常增长告警 |
| 线程池活跃数、队列深度、拒绝数 | 高水位或拒绝告警 |
| 落库成功、失败、重复数 | 成功率下降告警 |
| 事件发生到落库延迟 | 超过约定阈值告警 |
| Outbox 待投递、重试、死信数 | 积压或死信告警 |
| 表容量、分区、索引膨胀 | 接近容量水位告警 |

应用日志只输出 `eventId`、`source`、`actionCode`、异常类型等定位信息。日志系统不能作为唯一审计存储。

## 14. 发布与回滚

### 14.1 发布顺序

1. 执行审计表、索引和必要的 Outbox 数据库变更；
2. 发布具备审计基础能力但只开启少量试点动作的应用；
3. 验证指标、业务延迟和数据正确性；
4. 扩大动作覆盖；
5. 最后开放查询和导出接口。

### 14.2 回滚原则

- 审计应提供受控开关或发布器降级能力，但关闭行为必须被监控；
- 回滚应用时保留已经写入的审计数据；
- 数据库变更优先向后兼容，紧急回滚不删除表和历史数据；
- Outbox/MQ 回滚前暂停投递并记录消费位点；
- 回滚后核对缺失时间窗；补录必须注明来源和真实发生时间，不能伪造成实时事件。
